PiWork 的旧权限模型由 Pi 参数、角色工具列表、Extension 配置和 Connector 自身检查分别裁决，配置变化可在同一 Run 内扩权且未知工具缺少统一的 fail-closed 行为；我们决定让 Rust `CapabilityBroker` 在 Run 启动前编译并持久化版本化、不可变的 `RunCapabilitySnapshot`，把 Work/Assignment/Agent 身份、规范 Workspace、PermissionMode、Expert Pack、Host Tool 与 Extension Tool 的精确集合冻结下来，Host Tool 每次调用重新读取该快照，先持久化 Allow/Deny/Ask 决策与可恢复的 Approval request，Allow 再建立执行审计并将实际结果关联回决策，Pi 仅加载实时 Extension 与快照的交集，Connector 和 Workspace policy 只能进一步收窄权限，撤销、过期、越界、未知操作、审计写入失败或 Broker 故障一律拒绝；仅把 manifest 留在内存、信任 Adapter 的 allowlist、或在调用时回读可变配置的方案被否决，因为它们无法在重启后恢复权威事实，也无法证明实际执行与授权来自同一决策；其后果是所有能力都能追溯到 SQLite 中的 Run 快照、决策与执行结果并支持即时撤销，但新增 Adapter 必须把操作归一化到 Broker 词汇且不得拥有独立的最终权限权威。
